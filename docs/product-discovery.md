# Product discovery and selection

Status: planned.

## User experience

Example request:

> Add млеко 3,2% битолско плаво.

Also support requests such as `mleko 3.2% bitolsko plavo`, mixed scripts, casing differences, and decimal commas.

The assistant broadens the request for retrieval, the server finds and ranks actual products, and an interactive view lets the user select a product and quantity before adding it to the shared list.

```text
User's original request
  -> host assistant extracts broad search terms and preferences
  -> product-discovery MCP tool
  -> NajdiCena search, including pagination
  -> open-weight model matches candidates against original request
  -> merge relevant purchase-history products and deduplicate
  -> user chooses product and quantity in shopping UI
  -> persist exact selection through app-visible add tool
```

## 1. Interpret the query without losing intent

The host assistant prepares a broad query such as `млеко`, with other useful keywords as optional follow-up searches. The MCP tool must receive the **original query** as well as the generalized search terms.

Illustrative input, not a committed schema:

```json
{
  "spaceId": "space-id",
  "originalQuery": "млеко 3,2% битолско плаво",
  "searchTerms": ["млеко"],
  "preferences": {
    "brandText": "битолско",
    "fatPercent": "3.2",
    "packagingHint": "плаво"
  }
}
```

- Normalize Latin/Cyrillic forms for retrieval and matching while retaining the original spelling.
- Treat `3,2%` and `3.2%` as equivalent.
- Do not invent a pack size when the user did not give one.
- A packaging hint such as “blue” may be ambiguous. Do not infer an exact variant from it without supporting candidate data.
- Keep shopping quantity separate from product attributes such as fat percentage and pack size.
- The server must be able to derive a basic fallback search when the assistant provides only the original query.

## 2. Search NajdiCena

Proposed model-visible tool: `shopping_find_products` (read-only, scoped by `spaceId`).

The server calls the [NajdiCena integration](najdicena-integration.md), collects candidate offers, and returns a selection view after matching and history merging. The host should not need to pass a large raw catalog back into a second tool call.

Retrieve all pages within configured request, time, and candidate budgets. Do not silently treat the first page as the complete catalog. If a budget is reached, return `truncated: true` and allow refinement or more results.

Broad search is for recall. For example, NajdiCena's `млеко` results can include wafers containing milk; those need filtering during matching.

## 3. Match candidates through Vercel AI Gateway

Use an open-weight model through Vercel AI Gateway to compare every retrieved candidate against the **original user query**, including explicit preferences. The requested model was described as “Laya”; the exact model name and Gateway model ID need confirmation before implementation.

Send a compact projection of candidate data: candidate ID, name, description, and any supported brand, variant, pack-size, or packaging attributes. Batch larger result sets within the model's context and configured latency limits.

Require validated structured output, for example:

```json
{
  "matches": [
    {
      "candidateId": "candidate-1",
      "relevance": "strong",
      "reason": "Milk with the requested brand and 3.2% fat; packaging color is unverified.",
      "unverifiedAttributes": ["packagingColor"]
    }
  ],
  "rejectedCandidateIds": ["candidate-2"]
}
```

- Accept only candidate IDs supplied in the request; validate that every candidate is accounted for exactly once.
- Reject explicit contradictions such as another brand or fat percentage as exact matches. Label alternatives separately if shown.
- Represent missing evidence as uncertain rather than inventing attributes.
- Keep source prices and product details attached by application code, not generated by the model.
- Treat product text as data, not instructions.
- Use a configurable model ID and bounded concurrency. On failure, show relevant history and clearly labeled unranked source results, or offer a retry; do not claim model verification succeeded.

## 4. Combine with previous purchases

After matching catalog results, retrieve relevant products previously bought by the authenticated user in the requested space. Merge these with the matches, preserving badges such as “bought before,” purchase count, and last purchase date.

- Only history relevant to the current query belongs in this result set.
- Apply the same explicit brand/variant constraints to historical products.
- Deduplicate by established product identity, combining historical preference and current offers into one choice where possible.
- Purchase history can influence ordering, but must not override an explicit new preference.
- Historical prices are labeled as historical; refresh offers before showing them as current prices.
- A historical product with no current offer can still be selectable, with price/availability marked unknown.

### History requires a new lifecycle

Today, `shoppingService.clearItems` deletes rows. There is no persisted purchase event or purchaser on a shopping item.

Proposed behavior:

- Record an explicit “mark purchased” action with actor, space, product identity, quantity, and timestamp.
- Atomically save purchase history and remove/complete the corresponding active list rows.
- Removing an unwanted item is a separate action and does not count as a purchase.
- Track confirmed selections separately if useful; an added or selected item is not automatically a bought item.
- Initially read only the acting user's purchase history in the selected space. Household-wide suggestions can be a later explicit feature.

## 5. Selection UI and saving

Extend the existing MCP Apps shopping UI with a product-selection view. Each choice should show:

- Product name, brand/variant/pack size where known.
- Current offers or lowest observed valid price, store/branch, and update time.
- Match explanation and unresolved attributes.
- Purchase-history badges when applicable.
- Quantity control and an explicit Add action.

Group offers for the same exact product under one product choice. Selecting a product should normally preserve the ability to compare stores later; an explicit store preference is stored separately.

Extend `shopping_ui_add_items` to persist the chosen catalog reference and original query alongside the display name and quantity. Validate the selected reference against server-resolved candidates rather than trusting UI-supplied prices. Preserve the existing support for multiple items in one draft and the space picker.

If the user chooses to change spaces, reload history and revalidate the selection for that space. Show enough initial results to keep the UI usable, with more results accessible rather than silently dropping matches.

When nothing matches, allow query refinement or adding a free-text item. Free-text items remain unresolved for exact-price comparison until the user selects a product.

## Acceptance examples

- Cyrillic and Latin versions of the milk query find equivalent relevant candidates.
- A milk-containing wafer is rejected as a match for drinking milk.
- Milk with a different fat percentage is not labeled an exact match for `3,2%`.
- Previously bought matching milk appears once, with its history badge and current offers when available.
- No shopping row is written until the user confirms Add.
- An upstream/model failure does not create a fake match or discard the user's original request.
